# Disk is the source of truth; the Shadow Workspace lives for one tool call

The file on disk is always authoritative. Kronstadt keeps no document state between tool calls. A write tool loads the files it touches from disk, opens them in the language server (`didOpen`), applies and validates the edit through `didChange`, writes it back, then sends `didSave` and `didClose`. That transient set of open documents is the Shadow Workspace. Read tools follow the same rule: every tool closes every document it opened before it returns. The `CodeIntelligence` port enforces this rule, not each tool: documents can only be analysed inside a session, a tool call opens at most one, and when the session ends, however it ends, every document it opened is closed. A document another session still holds stays open until that session ends too. Decided in [#42](https://github.com/abellagonzalo/kronstadt/issues/42).

kotlin-lsp treats an open document as authoritative over disk, so a document left open stops tracking edits made outside Kronstadt. These come from the user's IDE, Claude's Edit tool, shell commands, and `git checkout` or rebase in the worktree. Closing everything at the end of each call hands those files back to kotlin-lsp's own file watcher. Kronstadt therefore needs no watcher, no mtime polling, no reload logic and no conflict state.

Write-back is guarded:
- Kronstadt writes only if the file's current content hash still matches the bytes the edit was based on. On a mismatch it rejects the edit with "changed on disk since read; re-read and retry". It never merges.
- A file the edit creates ([#70](https://github.com/abellagonzalo/kronstadt/issues/70)) has no bytes to hash, so its check is that it is still absent. If it appeared on disk in the meantime, the edit is rejected the same way. It is written through a temp file and a rename that never replaces an existing file, after creating its missing parent directories.
- It writes through a temp file and an atomic rename, keeping the file's permissions.
- Write tools run one at a time under a single lock per Kronstadt instance. Read tools don't take the lock.

## Consequences

- Write-back across several files checks every file's hash before writing any of them, so a hash mismatch writes nothing. Once writing starts there is no rollback: if a write fails partway (an I/O error, or a file changed between the check and its rename), the Edit reports a partial Write-back that names the files already written. Restoring the original bytes was rejected as complexity for a rare case, since Kronstadt promises no transactions on disk. Decided in [#43](https://github.com/abellagonzalo/kronstadt/issues/43).
- An edit made outside Kronstadt can be missing from `workspace/symbol` (`kt_find_symbol`) for a few seconds, until kotlin-lsp's watcher re-indexes it. A live test measured about 5 s for one file. We accept this lag. A watcher or check-on-use can be added later if evaluation shows the lag hurts.
- No validated Edit survives a tool call; the last rejected Edit is kept in memory until the next write call, so it can be amended; an amend that fails on its own Operations, finds the index not ready, or names another id keeps it for the call after ([#120](https://github.com/abellagonzalo/kronstadt/issues/120)). It never reaches disk, and amending it re-checks the original file hashes ([#88](https://github.com/abellagonzalo/kronstadt/issues/88)). A multi-step edit that passes through broken intermediate states must be sent as one batch in a single call. A begin/commit flow across calls is not possible in v1.
- We don't know whether kotlin-lsp rereads the disk as soon as it gets `didSave`/`didClose`. An acceptance test must show that `kt_find_symbol` sees an edit immediately after Write-back. If it doesn't, the fallback is to keep the written file open until the next call touches it. Settled in [#25](https://github.com/abellagonzalo/kronstadt/issues/25): kotlin-lsp 271.2085.0 doesn't (neither does `workspace/didChangeWatchedFiles`), so `LspCodeIntelligence` keeps a written document open after `didSave`, past the end of its session, for as long as later sessions read that same text from disk. The first session that reads different text (an outside change) syncs it and closes the document when it ends, handing the file back to the watcher. This stays inside the lsp adapter; the port doesn't mention it. kotlin-lsp analyses every file against the open text of the others, so a written file left open would hide an outside change from analyses of other files too, until a call touched that file. So every call first checks the documents Kronstadt keeps open against disk ([#56](https://github.com/abellagonzalo/kronstadt/issues/56)): one whose file changed is synced to the disk text and closed when that call ends, and one whose file was deleted is closed. An outside change therefore reaches kotlin-lsp at the next tool call, whichever file that call touches.

## Considered options

- **Long-lived Shadow Workspace plus a native file watcher**: rejected. A watcher alone has a race: a call can arrive before the event does. It also brings debouncing for `git checkout` storms and stale or conflict states.
- **Long-lived Shadow Workspace plus check-on-use (mtime/hash before every call)**: rejected for v1. It is correct but adds reload and conflict logic that nothing needs while no state survives a call.
- **Shadow Workspace as a separate directory on disk**: rejected. kotlin-lsp would index it as a second project, which costs a cold index of several GB.
