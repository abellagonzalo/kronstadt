# Edit whole Symbol Spans through one batched kt_edit tool

Agents change code with a single `kt_edit` tool that takes an ordered list of Operations: `replace`, `insert_before`, `insert_after`, `delete` and `edit_in`. Each Operation names a Symbol Path (`create`, added later, names a new file instead). `replace` and `delete` act on the whole Symbol Span: KDoc or the comments directly above, annotations, modifiers, the declaration, and a comment at the end of its last line. The agent sends the complete new text, and Kronstadt keeps nothing from the old span implicitly. `kt_read_symbol` returns exactly that span, so the agent always sees what it will replace. A small change inside a large Symbol uses `edit_in`: an exact string that must occur once inside the span, replaced literally.

Operations run in order against the Shadow Workspace, and each resolves its Symbol Path against the state the previous Operation left. They may span several files. The Edit gets one Validation and one all-or-nothing Write-back. Rename is a separate tool, `kt_rename_symbol`, because kotlin-lsp computes it across files and it can't be batched.

## Considered options

- **Body-only replace (Serena's `replace_symbol_body`)**: rejected. Serena's most common bug is a replace that reports `OK` but silently corrupts the file, because the server's range doesn't match what the agent thinks the "body" is. A span the agent reads verbatim removes that guess.
- **One tool per Operation**: rejected. ADR 0003 forces multi-step edits that pass through broken states into one call, and per-Operation tools can't mix Operation types in a batch. Per-Operation tools plus a separate batch tool would offer two ways to do the same thing.
- **Keeping the old KDoc or annotations when the new text omits them**: rejected as implicit magic. Omitting them deletes them.
- **Whitespace-tolerant or regex matching in `edit_in`**: rejected because a fuzzy match produces a confident wrong edit.

## Consequences

- Rewriting one line of a large function costs either a full-span `replace` or an `edit_in` with exact text. Agents must copy that text from `kt_read_symbol` output, which is why that output has no line-number gutter.
- Kronstadt trusts kotlin-lsp's `range` as the span, with three guards: the text at `selectionRange` must equal the name, the span extends to whole lines only when nothing else shares those lines, and Validation catches the rest. A list separator (`,`) right after the range, with or without an end-of-line comment after it, counts as part of the span rather than as other code: kotlin-lsp ends a constructor property's range before its trailing comma. A `;` still counts as other code. Added in [#68 A constructor val on its own line with a trailing comma can't be read or edited](https://github.com/abellagonzalo/kronstadt/issues/68). A change in how kotlin-lsp attaches comments changes the Symbol Span, which is another reason for the tested-version warning in ADR 0001.
- A Symbol with no whole-line span is refused, both for reading and for editing; a primary constructor always is, since its range starts on the class head's line. `kt_read_symbol` points to the enclosing Symbol. `kt_edit` points to a whole-file `edit_in` on that file (no Symbol Path) instead, because replacing the enclosing Symbol costs more, and that Symbol may share a line too. Letting `edit_in` match inside the raw `range` was rejected, because the agent couldn't read that text through `kt_read_symbol`. Added in [#99 A primary constructor can't be read or edited on its own: it always shares its first line with the class head](https://github.com/abellagonzalo/kronstadt/issues/99).
- Imports are explicit: each Operation may list imports to add. Kronstadt never applies organize-imports. The one exception is that an Edit removes the imports it made unused: those used before the Edit and unused after it, in the files it changed, other than those its Operations listed. It lists each one in its result. Imports that were already unused are never touched, and nothing is reordered. Kronstadt asks the code intelligence which of each changed file's imports are Unused Imports in its text before and after the Edit, and applies nothing it suggests. Without an answer about the text after the Edit, an import counts as used. Added in [#77 kt_edit: a delete or replace leaves imports only the removed code used](https://github.com/abellagonzalo/kronstadt/issues/77). The `lsp` adapter answers for kotlin-lsp, which has no unused-import diagnostic: it runs organize-imports on the text, reads which imports it would drop (not merely respell as or from a star import), and applies none of its edit. Organize-imports collapses a package into a star import once 5 of its names are used, so its answer can't tell whether an explicit import that a star new in its answer covers is used. Such an import counts as unused only if removing it from the text adds no error to the file's diagnostics. Without an answer in time, the import is undecided. Added in [#81 kt_edit: a replace in a multi-Operation batch left an import it made unused](https://github.com/abellagonzalo/kronstadt/issues/81). `kt_rename_symbol` follows the same rule. kotlin-lsp's rename answer also deletes imports that were already unused in the files it touches, so Kronstadt puts back every import the rename removed (other than the renamed Symbol's own, respelled with its new name) and removes again only those the same check finds the rename made unused. Added in [#85 kt_rename_symbol misreports its result](https://github.com/abellagonzalo/kronstadt/issues/85). A file's imports can depend on another changed file, e.g. when a member renamed or added there shadows an imported extension, so the change is judged as a whole: every changed file is brought to its text after the Edit before any is asked about that text, and every one to its text before the Edit before any is asked about that. Added in [#138 Removing imports made unused judges every edited file against every other edited file's current text](https://github.com/abellagonzalo/kronstadt/issues/138). Moved to the adapter in [#174 kotlin-lsp's rename and organize-imports quirks live in the lsp adapter, not core](https://github.com/abellagonzalo/kronstadt/issues/174). Being unsure keeps an import on both sides of the change: the code intelligence answers which imports are unused and which it can't decide about, and an import it can't show was used before the change is kept, as maybe already unused. So a change to a file whose text before it gives no answer, e.g. one that didn't compile, removes nothing it can't prove it made unused, whether or not the file compiles after it. Such a change may leave an import it really did make unused, which is visible and harmless; removing one that was already unused isn't. kotlin-lsp 271.2085.0's organize-imports does still drop exactly the unreferenced imports of a text with unresolved references; the adapter reports every import undecided when it gets no organize-imports answer, and an import a new star covers when the removal check doesn't settle it. Added in [#193 kt_edit removes imports that were already unused when the target file had compile errors before the Edit](https://github.com/abellagonzalo/kronstadt/issues/193). Every import kept for want of an answer is listed in the result, apart from those removed: one unused after the change but undecided before it, and one undecided after it unless the text before it shows it was already unused. So imports already unused are never listed. Each of a changed file's two questions, about its text after the change and before it, has its own budget as long as Validation's, so a file whose checks are slow can't leave the files asked after it with no time and their imports silently kept. A collapsed package leaves every explicit import of it undecided, most of them still used, and removing each in turn cost a file 2 diagnostics round-trips plus one per import. The `lsp` adapter now counts such an import as used, without a removal check, when the file's code refers to its name (outside comments, string literals and the package and import lines, and not as a member after a `.`), which settles most of them. A local declaration shadowing the name only keeps an unused import. Added in [#209 kt_edit: in a multi-file batch of deletes, imports made unused are removed in some files but kept in others](https://github.com/abellagonzalo/kronstadt/issues/209).
- `edit_in` also accepts a file target: `file` set and no Symbol Path. Its span is the whole file, so the exact string may sit anywhere in it. This covers text that belongs to no Symbol (the package line, file headers, file annotations, removing imports). It is the only way to change those lines, because Claude Code's `Edit` is denied on existing `.kt` files. `replace`, `insert_*` and `delete` still need a Symbol Path. Added in [#13 How does Kronstadt steer Claude Code agents to its tools instead of Read, Edit and grep?](https://github.com/abellagonzalo/kronstadt/issues/13).
- A whole-file `edit_in` whose text lies inside a Symbol's span counts as an edit of that Symbol: it replaces the innermost addressable Symbol Span holding the text's lines, which is what an `edit_in` on that Symbol would replace. The result lists that Symbol, and Validation prefers errors on its lines, the same as for the Symbol target. Symbols that share a line with other code have no Symbol Span, so they are skipped. Text outside every Symbol (the package line, imports), or text that crosses from one Symbol into another, still replaces only its own lines and lists no Symbol. Added in [#62 kt_edit: a whole-file edit_in that changes lines inside a Symbol lists no Symbol in its result](https://github.com/abellagonzalo/kronstadt/issues/62). The change, not `old`'s match, decides the Symbol: the lines `old` and `new` share at their start and end are left out, and the innermost Symbol Span holding the lines that remain counts as edited. Agents often widen `old` past a Symbol's end to make it unique, and only the Symbol they changed is listed. A change that itself crosses from one Symbol into another, or lies outside every Symbol, lists none. Lines only inserted or deleted could often go in several places with the same result (a function added after another, repeating its closing brace, could also go before that brace): they count as inside a Symbol only if every such place is, and lines only inserted only if the lines on both sides of them are too. So a blank line or a function added between two functions lists neither of them. The text written is the same either way. Added in [#129](https://github.com/abellagonzalo/kronstadt/issues/129).
- `edit_in`'s `old` must not start inside a line's indentation, after some of its leading whitespace but not all of it. `new` is spliced in as written, so the leftover indentation would stay on its first line only and its lines would no longer line up. The result still compiles, so Validation can't catch it. Such an Operation fails, naming the line, and nothing is written. Starting at the beginning of the line, right after the indentation or mid-line works as before. Re-indenting `new` was rejected as implicit magic, like fuzzy matching. Added in [#91 kt_edit edit_in: an 'old' that starts inside a line's indentation leaves the new lines mis-indented, and Validation can't tell](https://github.com/abellagonzalo/kronstadt/issues/91).
- An `edit_in` whose `old` occurs nowhere exactly, but occurs once if each line's leading whitespace is ignored, still fails, and its error names the line where that match starts and how the indentation differs: both indents when every line differs the same way, else just that it differs. `kt_get_definition`'s `at` gets the same hint. The hint is only an error message: nothing is ever applied on a match that ignores indentation, so the rule against whitespace-tolerant matching holds. Added in [#93 kt_edit edit_in: when 'old' matches only with different indentation, the error should say so](https://github.com/abellagonzalo/kronstadt/issues/93). When the indents describe a later line than the match's start (its first line starts mid-line without indentation), the error names that line too. Added in [#115](https://github.com/abellagonzalo/kronstadt/issues/115).
- `edit_in`'s exact match, and `kt_get_definition`'s `at`, treat every line ending as equal: each line break in `old` (`\n`, `\r\n` or a lone `\r`) matches one whole line break in the file, of any of those kinds, and never half of a `\r\n`. Agents can't see a file's line endings or reliably reproduce them, so a multi-line `old` sent with `\n` would never match in a CRLF file. All other whitespace stays exact, so the rejection of whitespace-tolerant matching still holds. Added in [#61 kt_edit edit_in: a multi-line 'old' never matches in a CRLF file, and the error doesn't say why](https://github.com/abellagonzalo/kronstadt/issues/61).
- `create` makes a new `.kt`/`.kts` file inside the batch: a `file` that must not exist and `code`, its whole text. The new file joins the Shadow Workspace with an empty base, so every error in it is new: it is validated and written back with the rest of the Edit, and new files no longer bypass Validation through Claude Code's `Write`. Later Operations can target its Symbols, passing its file. Missing parent directories are created only during Write-back, so a rejected Edit leaves none behind. Kronstadt doesn't check the package line against the directory, since Kotlin allows a mismatch. Deleting, moving or renaming files stays out of `kt_edit`. Added in [#70 kt_edit can't create a new .kt file, so new classes and test files bypass Validation](https://github.com/abellagonzalo/kronstadt/issues/70).
