# Edit whole Symbol Spans through one batched kt_edit tool

Agents change code with a single `kt_edit` tool that takes an ordered list of Operations: `replace`, `insert_before`, `insert_after`, `delete` and `edit_in`. Each Operation names a Symbol Path (`create`, added later, names a new file instead). `replace` and `delete` act on the whole Symbol Span: KDoc or the comments directly above, annotations, modifiers, the declaration, and a comment at the end of its last line. The agent sends the complete new text, and Kronstadt keeps nothing from the old span implicitly. `kt_read_symbol` returns exactly that span, so the agent always sees what it will replace. A small change inside a large Symbol uses `edit_in`: an exact string that must occur once inside the span, replaced literally.

Operations run in order against the Shadow Workspace, and each resolves its Symbol Path against the state the previous Operation left. They may span several files. The Edit gets one Validation and one all-or-nothing Write-back. Rename is a separate tool, `kt_rename_symbol`, because kotlin-lsp computes it across files and it can't be batched.

## Considered options

- **Body-only replace (Serena's `replace_symbol_body`)**: rejected. Serena's most common bug is a replace that reports `OK` but silently corrupts the file, because the server's range doesn't match what the agent thinks the "body" is. A span the agent reads verbatim removes that guess.
- **One tool per Operation**: rejected. ADR 0003 forces multi-step edits that pass through broken states into one call, and per-Operation tools can't mix Operation types in a batch. Per-Operation tools plus a separate batch tool would offer two ways to do the same thing.
- **Keeping the old KDoc or annotations when the new text omits them**: rejected as implicit magic. Omitting them deletes them.
- **Whitespace-tolerant or regex matching in `edit_in`**: rejected because a fuzzy match produces a confident wrong edit.

## Consequences

- Rewriting one line of a large function costs either a full-span `replace` or an `edit_in` with exact text. Agents must copy that text from `kt_read_symbol` output, which is why that output has no line-number gutter.
- Kronstadt trusts kotlin-lsp's `range` as the span, with three guards: the text at `selectionRange` must equal the name, the span extends to whole lines only when nothing else shares those lines, and Validation catches the rest. A change in how kotlin-lsp attaches comments changes the Symbol Span, which is another reason for the tested-version warning in ADR 0001.
- Imports are explicit: each Operation may list imports to add. Kronstadt never applies organize-imports. The one exception is that an Edit removes the imports it made unused: those used before the Edit and unused after it, in the files it changed, other than those its Operations listed. It lists each one in its result. Imports that were already unused are never touched, and nothing is reordered. kotlin-lsp decides what is unused: it has no unused-import diagnostic, so Kronstadt asks its organize-imports command about each changed file's text before and after the Edit, reads which imports it would drop (not merely respell as or from a star import), and applies none of its edit. Without an answer, an import counts as used. Added in [#77 kt_edit: a delete or replace leaves imports only the removed code used](https://github.com/abellagonzalo/kronstadt/issues/77).
- `edit_in` also accepts a file target: `file` set and no Symbol Path. Its span is the whole file, so the exact string may sit anywhere in it. This covers text that belongs to no Symbol (the package line, file headers, file annotations, removing imports). It is the only way to change those lines, because Claude Code's `Edit` is denied on existing `.kt` files. `replace`, `insert_*` and `delete` still need a Symbol Path. Added in [#13 How does Kronstadt steer Claude Code agents to its tools instead of Read, Edit and grep?](https://github.com/abellagonzalo/kronstadt/issues/13).
- `create` makes a new `.kt`/`.kts` file inside the batch: a `file` that must not exist and `code`, its whole text. The new file joins the Shadow Workspace with an empty base, so every error in it is new: it is validated and written back with the rest of the Edit, and new files no longer bypass Validation through Claude Code's `Write`. Later Operations can target its Symbols, passing its file. Missing parent directories are created only during Write-back, so a rejected Edit leaves none behind. Kronstadt doesn't check the package line against the directory, since Kotlin allows a mismatch. Deleting, moving or renaming files stays out of `kt_edit`. Added in [#70 kt_edit can't create a new .kt file, so new classes and test files bypass Validation](https://github.com/abellagonzalo/kronstadt/issues/70).
